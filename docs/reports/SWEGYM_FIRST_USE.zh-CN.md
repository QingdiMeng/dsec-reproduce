## 准备阶段发现的问题

1. 数据集 ID `python__mypy` 和发布的镜像名称 `python_s_mypy` 不同。按数据集名称推断镜像名导致仓库返回 401。通过官方发布者的 Hub 元数据找到了正确的公开镜像。
2. 部分层拉取完毕后，客户端因 90 秒镜像拉取超时而中断。继续拉取同一不可变镜像时成功复用已有层。期间没有重启守护进程、代理配置或宿主服务。
3. 官方镜像假定以 root 安装 pip 包，而 DSec 任务以 UID 1000 运行。仓库已经可写，Conda 的 site-packages 目录属于 root。应准备可写 HOME 和 pip 用户安装配置，无需授予任务 root 权限，也无需递归复制 Conda 层或更改其所有者。
4. `make_test_spec` 还会生成构建时环境规格，并可能拉取依赖。对冻结的实例镜像，适配器直接使用同一套官方 `make_eval_script_list` 和 `TestSpec.eval_script`，评测命令、预期测试及官方评分器均保持原样。
5. 此时单条 verifier 命令限时 30 秒。入口必须显式报告验证未完成，不能静默计为 0 分。长任务支持仍是待验收的集成条件。
6. 整个目录清单绑定到同一摘要，导致新增任务镜像后无法读取旧实例历史。增量更新现可显式固定目录历史，旧环境、CID 池和宿主／网络策略必须完全一致。镜像或限额变化、摘要未知、历史漂移均会被拒绝。旧实例日志无需改写，在现有固定 Node 范围内发布环境也无需新增 root 权限。
7. 首次正式 API 创建已经到达 guest 镜像导入阶段，随后耗尽原有 15 秒认证及就绪等待时间。任务尚未进入评测，失败实例已完全回收，未残留 CID 或私有盘。新增由运维固定的独立 guest 启动预算（1–240 秒），QMP 期限仍为 15 秒，工具命令限制不变。新环境 ID 携带该预算，原环境及失败记录照旧保留。认证与任务就绪共享同一截止时间。
8. 初版私有编排脚本重新序列化目录时多加了一个换行，部署摘要与保存的输入摘要不同，后续升级正确拒绝了这段历史。应固定实际部署的字节并逐字节复制目录，保持摘要校验。重试前通过只读预检检查了全部历史描述符。
9. 修正启动等待后，guest Docker 的 `vfs` 导入器复制各层累积内容，耗尽 guest 的 8 GiB 磁盘，而宿主仍有空间。guest 构建器现显式选择 `vfs` 或 `overlay2`，不自动回退。SWE-Gym guest 的 ext4 根盘选用 `overlay2`。改动仅作用于准备的 guest，物理宿主 Docker 驱动保持不变。
10. 本地 RPC 把带类型的 `ServiceError` 序列化成字面类型 `ServiceError`，导致清理详情丢失。修复使原始错误类别和详情经现有 RPC 以及已提交创建请求的响应传递。真实本地 RPC 回归确认客户端能收到清理证明。
11. 官方镜像的 Git 未实现 `git apply --allow-empty`。预测补丁为零字节时跳过应用补丁，仍执行完整官方 verifier。非空补丁使用普通 `git apply -v`。工具调用错误应记为无效证据，不能算负奖励。验收同时要求官方测试报告和预期数值，防止补丁被拒绝却被误判为基线通过。
12. 目录 `/testbed` 可写并不意味着其中已有的 `mypy.egg-info` 可写。下一对运行进入官方测试并取得 0/1，但日志显示 pytest 继续运行前官方可编辑安装已失败。通过导出已停止的容器并使用 Docker `COPY --chown`，生成内容相同、仓库归 UID 1000 所有的派生镜像。整个过程不在物理宿主运行任务代码或改动 Conda。重新运行两组，同时检查安装输出与测试状态。

<a id="training-boundary"></a>

## 训练边界

预期目标是 [单次 rollout 异步优化（SAO）](https://arxiv.org/html/2607.07508)，有别于异步 GRPO。Critic 训练、行为策略对数概率、策略版本跟踪和观测掩码归外部 trainer／agent 适配器负责。DSec 负责沙盒生命周期、调度、执行证据和恢复。宣称 SAO 训练通过前，还需使用现有 16 GiB GPU 和本地模型／框架，单独验证 actor 与 critic 的显存可行性。

参考资料见 [SWE-Gym 项目](https://github.com/SWE-Gym/SWE-Gym)、[官方环境／评分分支](https://github.com/SWE-Gym/SWE-Bench-Fork)。

<a id="direct-io-acceptance"></a>

### Direct I/O 验收

新增显式环境模式 `disk_cache: direct`，既有记录仍使用缓冲 I/O。Direct I/O 绕过宿主磁盘页的额外副本，保留 flush，不提高 guest 内存、VMM 额度或 IAM 需求。回收时在内核移除 cgroup 前保存可读的峰值／OOM／CPU／I/O 计数器。未更改 root helper、启动器、宿主 Docker、防火墙策略或权限安装。

安装版修复通过正式 API 完成一对全新基线／标准答案验收（`api-direct-r1`），含官方可编辑安装与完整清理。独立观察证实，两台运行中实例的根盘文件描述符均带有 O_DIRECT。

| Episode | 分数 | Episode 耗时 | VMM cgroup 峰值 | 采样所得宿主脏页最大值 | OOM 杀进程数 |
| --- | --- | --- | --- | --- | --- |
| 基线 | 0 | 37.096 s | 1,108,639,744 B | 73,728 B | 0 |
| 标准答案 | 1 | 43.766 s | 1,106,644,992 B | 77,824 B | 0 |

峰值和 OOM 数据来自回收时保留的内核计数器。脏页最大值以 0.5 秒间隔采样，可能低于真实峰值。两次有界运行不足以验证长时或并发稳定性。Edge 复制镜像或计算哈希时的文件缓存位于 VMM cgroup 之外，仍可能存在。本修复不涉及 DAX、共享 guest RAM、热镜像发布或 Docker 资源对照。

核心回归发现 611 项，602 通过、9 项跳过。8 个受控宿主隔离变异通过。使用固定真实 harness 的可选应用测试 24 项通过。源码、wheel 和文档边界检查通过。完整模型与失败证据、token 审计、限定作用域的内核 OOM 日志和 direct I/O 审计保存在 2026-10-26 私有实验中，发行源码不含密钥或客户端凭据。模型服务停止，GPU 恢复到 35 MiB 空闲占用，私有 VM 磁盘／CID 均回收，原有宿主容器保持原样。
